# 小六记 — 开发规格（Spec）

## Problem Statement

用户希望在 iPhone 上便捷地记录每日消费，但目前主流记账方式依赖手动输入，步骤繁琐容易放弃；而现有 APP 方案又面临苹果非认证开发者证书每 7 天过期的困境。同时，用户已经保留了付款截图，却没有一个工具能自动从截图中提取关键信息并结构化记账。

核心痛点是：用户在付款后需要多步操作才能完成记账，且数据难以长期保存和深度分析。

---

## Solution

构建一个基于 PWA 的「小六记」记账应用，运行在 iPhone Safari 中，通过 iOS 快捷指令调用系统内置 OCR 自动识别付款截图，将金额、时间、商户等信息填入表单，用户确认后存入本地 IndexedDB。应用提供按时间、分类、记账人三个维度的统计图表，点击图表可穿透到明细列表，并支持导出 Excel/CSV 备份。

**核心流程**：
```
付款截图 → 快捷指令触发 → iOS系统OCR识别 → 填充表单 → 选择分类/记账人 → 确认保存 → IndexedDB → 统计图表
```

**技术栈**：SvelteKit + TypeScript + Tailwind CSS + ECharts + Dexie.js

## User Stories

### 认证与用户管理

1. 作为新用户，我希望注册一个本地账号，以便安全地使用应用
2. 作为已注册用户，我希望输入用户名和密码登录，以便访问我的账本
3. 作为用户，我希望记住登录状态（本地持久化），以便下次打开时无需重复登录
4. 作为用户，我希望修改登录密码，以便保护账号安全
5. 作为用户，我希望注销账号并删除所有本地数据，以便彻底清除我的账本
6. 作为家庭用户，我希望创建多个记账人账号，以便每个家庭成员可以独立记录自己的消费

### 消费记录管理

7. 作为用户，我希望通过 iOS 快捷指令从相册选择付款截图，以便可以快速启动记账流程
8. 作为用户，我希望应用自动识别截图中的金额、时间、商户名称，以便减少手动输入
9. 作为用户，我希望在 OCR 识别结果基础上进行人工校对和修改，以便确保数据准确
10. 作为用户，我希望手动添加消费记录（无需截图），以便在没有截图时也能记账
11. 作为用户，我希望为每笔消费选择分类（餐饮、交通、购物等），以便后续可以按分类统计
12. 作为用户，我希望手动选择记账人（多账户场景），以便区分不同人的消费
13. 作为用户，我希望为每笔消费添加备注，以便记录消费详情
14. 作为用户，我希望查看按日期排列的消费记录列表，以便回顾每日支出
15. 作为用户，我希望筛选消费记录（按日期范围、分类、记账人），以便快速定位特定消费
16. 作为用户，我希望编辑已有的消费记录，以便修正错误或补充信息
17. 作为用户，我希望删除消费记录，以便可以撤销误记的账单
18. 作为用户，我希望标记某笔消费为"退款"，以便可以冲抵之前的支出

### 消费分类管理

19. 作为用户，我希望使用预设的分类（餐饮、交通、购物、娱乐、医疗、教育等），以便快速记账
20. 作为用户，我希望自定义新的消费分类，以便适配我的消费习惯
21. 作为用户，我希望为自定义分类设置颜色标识，以便在图表中一目了然
22. 作为用户，我希望删除不再使用的自定义分类，以便保持分类简洁

### 统计与可视化

23. 作为用户，我希望看到当月的总支出概览，以便了解本月消费水平
24. 作为用户，我希望按时间周期（日/周/月）查看支出趋势，以便追踪消费变化
25. 作为用户，我希望按消费分类查看支出占比（饼图），以便了解钱花在哪里
26. 作为用户，我希望按记账人查看各自的消费情况，以便家庭账本清晰
27. 作为用户，我希望点击图表中的某个分类/月份/记账人，以便穿透到具体的消费明细列表
28. 作为用户，我希望查看消费明细列表，以便可以逐笔核对
29. 作为用户，我希望看到每日、每周、每月的收支汇总卡片，以便快速掌握消费节奏

### 预算管理

30. 作为用户，我希望为每个月设置总预算上限，以便控制月度消费
31. 作为用户，我希望查看当前月份的预算使用进度（已用/总额），以便实时了解是否超支
32. 作为用户，我希望在接近或超过预算时收到提醒，以便及时调整消费行为
33. 作为用户，我希望为特定分类单独设置预算，以便精细控制各类别支出

### 数据导出与备份

34. 作为用户，我希望将消费记录导出为 CSV 文件，以便可以在电脑上用 Excel 打开
35. 作为用户，我希望将消费记录导出为 Excel 文件，以便获得格式更友好的报表
36. 作为用户，我希望按日期范围或分类筛选后导出，以便获得定制化的报表
37. 作为用户，我希望将全部数据导出为 JSON 备份文件，以便可以安全存储

### PWA 特性

38. 作为用户，我希望将应用添加到 iPhone 主屏幕，以便像原生 APP 一样使用
39. 作为用户，我希望应用离线时仍能查看已保存的记录，以便没有网络也能记账
40. 作为用户，我希望应用有合适的启动画面和图标，以便体验接近原生 APP

## Implementation Decisions

### 架构决策

1. **PWA 优先**：不开发原生 APP，通过 Safari「添加到主屏幕」使用，避免证书过期问题
2. **本地优先存储**：所有数据存储在浏览器 IndexedDB 中，不依赖云端服务，保证隐私和数据自主权
3. **iOS 快捷指令 + 系统 OCR**：利用 iOS 自带的 Vision Framework 进行 OCR 识别，免费、快速、离线可用
4. **前端全栈**：SvelteKit 模式下，数据库操作全部在前端完成（IndexedDB），无需后端服务

### 模块划分

| 模块 | 职责 |
|------|------|
| `auth` | 用户注册、登录、密码加密、会话管理 |
| `expense` | 消费记录的增删改查、OCR 数据解析、表单校验 |
| `category` | 分类的 CRUD、预设分类初始化、颜色配置 |
| `statistics` | 多维度聚合计算（时间/分类/记账人）、图表数据准备 |
| `budget` | 预算管理、进度计算、超支检测 |
| `export` | CSV/Excel/JSON 导出、文件下载 |
| `pwa` | Service Worker、离线缓存、manifest 配置 |
| `db` | IndexedDB 封装（Dexie.js）、数据迁移、版本管理 |

### 数据模型（Schema）

```typescript
interface User {
  id: number;           // 自增主键
  username: string;     // 唯一用户名
  password_hash: string; // bcrypt 哈希（本地）
  created_at: string;    // ISO 8601
}

interface Expense {
  id: number;
  user_id: number;       // 关联 User
  amount: number;        // 金额（分，整数存储避免浮点误差）
  category_id: number;   // 关联 Category
  merchant?: string;     // 商户名称（OCR识别）
  remark?: string;       // 备注
  is_refund: boolean;    // 是否退款
  paid_at: string;       // 消费时间
  created_at: string;    // 记录时间
}

interface Category {
  id: number;
  name: string;
  icon: string;          // emoji 或 icon name
  color: string;         // hex 颜色
  is_default: boolean;   // 是否系统预设
}

interface Budget {
  id: number;
  user_id: number;
  month: string;         // 'YYYY-MM'
  limit_cents: number;   // 预算上限（分）
  category_id?: number;  // 可选，null 表示总预算
}
```

### OCR 数据流

1. 用户在相册选择截图 → 快捷指令调用 Vision Framework OCR
2. OCR 返回文本，解析出金额（正则匹配数字）、时间（解析日期格式）、商户（首行或关键行）
3. 快捷指令通过 URL Scheme 打开 PWA 并传递参数
4. PWA 读取 URL 参数 → 填充表单 → 用户确认 → 保存

### 认证方案

- 密码使用 `bcrypt`（via `bcryptjs` 库）在前端本地哈希
- 登录成功后将 Token 存储在 IndexedDB（非 localStorage，避免 XSS）
- 无服务端，认证完全本地化

### 统计聚合策略

- 所有聚合计算在前端完成（IndexedDB 查询 + JavaScript 运算）
- 使用 IndexedDB 的范围查询 + 索引优化性能
- 图表数据按需计算，不预存聚合结果（保持数据一致性）

## Testing Decisions

### 测试策略

由于这是纯前端应用，测试主要关注业务逻辑层和数据层，而非 UI 层。

**高优先级测试区域**：

1. **数据层（Dexie.js 封装）**
   - 消费记录的 CRUD 操作是否正确
   - 索引查询是否高效（按 userId、paidAt、categoryId）
   - 数据迁移逻辑（schema 版本升级）

2. **统计计算层**
   - 按月份聚合：同月所有记录金额求和
   - 按分类占比：各分类金额 / 总金额
   - 按记账人拆分：userId 过滤正确

3. **认证层**
   - 密码哈希/验证流程正确
   - 会话持久化和清除正确

4. **导出层**
   - CSV 生成格式正确（UTF-8 BOM，中文不乱码）
   - Excel 生成内容完整
   - 筛选条件正确应用到导出数据

**不测试**：
- iOS 快捷指令的 OCR 识别（属于系统能力，外部依赖）
- Service Worker 的离线行为（需要真机测试，难以自动化）

## Out of Scope

以下内容不在本次开发范围内：

- 云端同步和多设备数据同步
- 多人共享账本（多人各自独立账本，非共享）
- 消费趋势的环比/同比分析
- 智能分类建议（AI 自动归类）
- 支付宝/微信 API 直连
- 安卓平台支持
- 桌面客户端
- 订阅/付费功能

## Further Notes

- **金额存储**：统一使用「分」为单位的整数，避免浮点数精度问题
- **日期格式**：统一使用 ISO 8601
- **PWA manifest**：需配置 display: standalone、theme_color、background_color 等以获得最佳体验
- **首次加载性能**：首屏应在 3 秒内加载完成
- **IndexedDB 容量**：预期用户数据量在千级别，单用户不超过 10MB
