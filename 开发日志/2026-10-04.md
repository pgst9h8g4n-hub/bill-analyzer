# 2026-10-04 统计页增强（预算对照 + 大额消费 TOP + 收支/中性数据层）

## 背景
统计页原有三卡（本月/本周/昨日 消费净额）+ 趋势图 + 分类饼图 + 分类明细，缺预算对照与大额消费排行。本轮补三块，并在数据层暴露收入/中性供后续扩展。

## 数据层（`src/lib/db/stats.ts`）
- `StatSummary` 扩字段：`monthIncome`（本月收入合计，cent）、`monthNeutralCount`/`monthNeutralTotal`（本月中性交易笔数/金额）、`monthRefund`（本月退款冲抵，cent）。
- 新增 `getMonthCompare(ledgerId)` → `CompareItem`：消费净额本月 vs 上月，`ratio=(本期-上期)/|上期|`，上期为 0 时 null。
- 新增 `getWeekCompare(ledgerId)` → `CompareItem`：消费净额本周（周一为起点）vs 上周。
- 新增 `getBudgetVsActual(ledgerId, month)` → `BudgetVsActual[]`：遍历 `db.budgets`，`categoryId==null` 的取全月消费净额，否则取该分类净额；返回 `ratio`（used/limit）+ `over`（实际>预算）。
- 新增 `getTopExpenses(ledgerId, month, limit=5)` → `TopExpense[]`：本月消费范围内单笔金额最大的 N 笔（排除退款/转账），带分类信息。

## 预算页（`src/routes/budget/+page.svelte`）
- `src/lib/db/budget.ts` 新增 `getCategorySpending(ledgerId, month, categoryId)`：某分类某月消费净额，`categoryId==null` 等价全月。
- 修 bug：分类预算进度条此前误用**总支出** `spending`，现改用该分类实际支出（`catSpending.get(budget.category_id)`），并在 `handleSave` 后刷新分类支出映射。总预算卡仍用总支出（口径正确）。

## 统计页周期不更新 + 分类图空白 根因修复（本轮）
用户实测「切某月数据不变、大额 TOP 混进 2/3 月、每日趋势/分类图空白」。上一会话定位到"前缀"层，本轮把两个真正的根因挖出并修复（均在 `src/lib/db/stats.ts`）：

**根因 1：周期函数把「单月」误判成「整年」前缀（切周期不更新的元凶）**
`getPeriodSummary`/`getPeriodTrend`/`getPeriodCategoryStats`/`getPeriodTopExpenses` 四个函数里，判断年/月用的写法是 `const [py, pm] = period.split('-'); const prefix = py !== pm ? py : ...`。
- 单月 `period='2026-05'` → `py='2026', pm='05'`，`py !== pm` 恒为 **true**（年串 `'2026'` 永不为月串 `'05'`），于是 `prefix = py = '2026'` —— 选「2026年5月」实际匹配的是 **2026 整年**，2/3/4 月的消费全被拉进来。这就是「切某月数据不变、大额 TOP 混月、每日趋势横轴刻度对不上」的根因。
- 年周期 `period='2026'` → `pm=undefined`，侥幸正确。
修复：改用 `pm` 真假判断（`pm` 存在即单月）：`const prefix = pm ? period + '-' : py;`（单月→`'2026-05-'`，整年→`'2026'`）。`getPeriodTrend` 的桶聚合 `keyOf` 同步改 `pm ? d.slice(0,10) : d.slice(0,7)`（单月按天、整年按月）。

**根因 2：分类统计 `total > 0` 过滤把正常消费全过滤掉（分类图空白的元凶）**
`getCategoryStats`/`getPeriodCategoryStats` 的 filter 写 `item.total > 0`。但消费净额 `expenseSigned` 消费记**负**、退款冲抵记正，正常某分类消费（净额为负）`total` 是负数 → 被 `> 0` 过滤掉 → 分类占比饼图/明细经常为空或只剩被退款冲正的极少数分类。修复：`total !== 0`（有消费就保留，按净额绝对值排序不变）。

**回归测试**：新增 `tests/stats-period.test.ts`（8 例，`fake-indexeddb` + vitest），造 2026 年 2/3/5 月各笔消费，断言「选 5 月只出 5 月、选 2026 出全年」「大额 TOP 不跨月」「趋势横轴随周期」，并含旧 bug 复现用例。旧逻辑跑 8/8 全失败（红），修复后 8/8 通过（绿）。devDependencies 加 `vitest` + `fake-indexeddb`，新增 `vitest.config.ts`（`$lib` 别名）。

验证：`npx vitest run` 8/8；`npx svelte-check` 0 errors（仅 settings 页 4 个既有 a11y 警告）；`npx vite build` 通过。

## 预算页"总预算不显示"三轮根因修复（用户实测"设总预算没反应"）
数据层本身一直是对的（`saveBudget` 把 `limit_cents`/`category_id` 都写进去了、`getBudgets` 也读得回，fake-indexeddb 复现脚本已验证），bug 全在**页面渲染层**，三轮挖出三个独立根因：

1. **onMount 误删月份列表**（上轮引入）：`loadForMonth` 里漏了 `getBudgetMonths` → `availableMonths` 恒空、月份下拉光秃秃。已补回，改由响应式 watcher（`loadedLedgerId`）在 `ledgerId` 就绪后触发 `loadForMonth`（`onMount` 里 `if(!ledgerId) return` 因 store 异步、mount 时恒 0 而失效，故删除）。
2. **Dexie schema 漏字段**（v1~v7）：`budgets` 表 7 个版本都只声明 `limit_cents`/`category_id` 之外的字段。虽不丢数据（值仍持久化），但 `.and(b => b.category_id===...)` 无索引可走、行为不可靠。新增 **v8**：`budgets: '...month, limit_cents, category_id'`（补两个普通索引，不重建表、不丢旧数据）。
3. **总预算卡 `totalBudget` 非响应式**（主因）：`totalBudget` 原是普通 `const`（Svelte 非响应式），`loadForMonth` 更新 `budgets` 后它**不重算**，`{#if totalBudget > 0}` 恒拿旧值 0 → 总预算卡永不渲染；而分类预算走 `{#each budgets}` 直接吃响应式数组故正常——正合用户"分类可以、总预算没反应"的现象。改为 `$:` 派生后，`progress`/`isOverBudget`/`remaining`（均 `$:`，依赖 `totalBudget`）连锁重算。

验证：`npx vitest run` 15/15（budget-delete 测试扩到 8 例，含"总预算 set→改值命中 update 不新增"、"null/0 脏数据合并"）；`npx svelte-check` 0 errors；`npx vite build` 通过。真实数据以 5173 强刷后实测为准。

## 优化轮（A#3 复合索引 / C#7 默认锚最新有数据月）
按优先级做了两项低风险优化（A#1 统计页本周/昨日卡已确认逻辑正确无需改；预算自动滚月、收入中性卡仍待确认）：

**A#3 复合索引隐患：saveBudget 补 user_id**
- `saveBudget` 写入时未填 `user_id`，`[user_id+month]` 复合索引对 undefined 行为不保证。`saveBudget` 增 `userId` 参数（`data.userId ?? 0`），新记录完整落 `user_id`。
- `Budget` 接口补 `user_id: number` 字段（Dexie schema 本来就有该列，只是 TS 接口漏了）。

**C#7 预算页默认锚到"最新有数据月"**
- 预算页 `selectedMonth` 原默认 `getCurrentMonth()`（10月），数据在 3 月时打开是空态看着像没数据。`loadForMonth` 拉完月份列表后，若当前月不在有数据月份里且用户未手动切过（`monthPinnedByUser` 标志），自动锚到 `availableMonths[0]`（最新有数据月）并重拉该月数据；用户点月份下拉后设 `monthPinnedByUser=true`，后续不再覆盖。
- 明细页本就是"看全部+分页"定位，不锁月份更合理，未改。
